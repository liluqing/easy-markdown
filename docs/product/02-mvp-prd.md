## 1. 产品概述

Easy Markdown 是一个本地优先、Git 原生、面向人类成员与 AI Agent 的团队文档工作区。

知识内容以普通 Markdown、TXT 和本地资源文件存在于用户选择的目录中。应用提供面向人的导航、编辑、预览、搜索和版本界面；Agent 直接通过文件系统读取和修改同一份内容。

## 2. 背景

团队目前使用语雀维护：

- 需求文档。
- 产品文档。
- 技术分析与技术方案。
- 测试用例。
- 测试计划。
- 其他项目过程文档。

现有问题包括：

- Agent 接入需要依赖语雀 API、Token 和产品支持的操作范围。
- 文档与代码仓库分离，Agent 需要在不同系统间建立上下文。
- Agent 批量修改后的差异审查和回滚不够自然。
- 团队无法将知识作为普通文件纳入已有工程工具链。

## 3. 产品目标

MVP 必须验证四个闭环：

1. 人类成员可以低门槛编辑和阅读本地文本知识。
2. Agent 无需产品私有 API 即可读取和修改知识。
3. 所有变化能够通过 Git 检查、记录和恢复。
4. 多成员可以通过现有 Git 远端完成可靠的异步协作。

## 4. 非目标

MVP 明确不做：

- 块编辑器和数据库视图。
- 实时多人共同编辑。
- 评论、@成员、消息和通知中心。
- 自建账号、组织和细粒度权限系统。
- 自建 Git 托管。
- 移动端和 Web 端。
- Word、Excel、PDF 的编辑。
- AI 问答、RAG 和向量数据库。
- 文档网站发布。
- 完整复刻语雀或 Notion。

## 5. 目标用户

### 5.1 文档作者

产品经理、开发人员、测试人员等需要创建和维护项目文档的成员。

核心诉求：编辑简单，不需要学习 Git 命令，文档不会因为同步而丢失。

### 5.2 知识消费者

需要搜索、阅读和引用项目知识的团队成员。

核心诉求：快速找到正确内容，链接和图片可以正常阅读。

### 5.3 Agent 操作者

使用编码 Agent 或通用 Agent 分析需求、生成方案、修改测试用例的成员。

核心诉求：Agent 能直接访问知识，同时所有写入都能被检查和撤销。

### 5.4 知识库管理员

负责语雀迁移、目录规范、Git 远端和团队流程的成员。

核心诉求：迁移可核验、主分支受保护、错误可恢复。

## 6. 核心使用场景

### 场景 A：编辑一篇需求文档

1. 用户打开知识库。
2. 从目录树找到或新建需求文档。
3. 在分栏模式编辑并预览。
4. 内容自动保存到本地文件。
5. 用户查看变化并创建一个版本。
6. 用户将版本同步到团队远端。

### 场景 B：Agent 根据需求更新测试用例

1. 用户在独立变更分支启动 Agent 任务。
2. Agent 读取需求、现有测试用例和相关技术文档。
3. Agent 直接修改 Markdown 文件。
4. 应用检测到外部变化，并展示逐文件差异。
5. 用户接受、继续修改或撤销变化。
6. 用户创建版本并提交远端评审。

### 场景 C：同步团队知识

1. 用户点击“同步”。
2. 应用获取远端变化。
3. 无冲突时更新本地并推送用户版本。
4. 有冲突时停止推送，进入冲突处理。
5. 用户确认最终内容后重新创建版本并同步。

### 场景 D：恢复错误修改

1. 用户发现文档被人或 Agent 错误修改。
2. 用户打开文档历史，查看版本差异。
3. 用户选择一个正确版本进行恢复。
4. 应用生成新的恢复变更，不改写共享历史。

## 7. 产品原则

### 7.1 文件是唯一真源

- 可编辑内容只保存在普通文件中。
- 搜索索引和缓存必须可以删除后重建。
- 应用退出后，文件仍能被其他工具正常使用。

### 7.2 保存、版本、同步相互独立

| 动作 | 用户含义 | 系统行为 |
| --- | --- | --- |
| 自动保存 | 防止本机内容丢失 | 写入本地文件 |
| 创建版本 | 记录一次有意义的修改 | 创建 Git Commit |
| 同步 | 与团队交换已经记录的版本 | 获取并推送远端 |

系统不得为每次键入创建 Commit。

### 7.3 不静默覆盖

发生以下情况时必须停止自动写入并提示用户：

- 本地未保存内容与外部文件修改冲突。
- Git 合并产生冲突。
- 文件已被删除或移动。
- 写入目标解析后位于知识库根目录之外。

### 7.4 Git 能力使用产品语言表达

| Git 概念 | 产品文案 |
| --- | --- |
| Commit | 创建版本 |
| Pull/Fetch | 获取团队更新 |
| Push | 上传版本 |
| Branch | 变更分支 |
| Diff | 修改内容 |
| Merge conflict | 内容冲突 |
| Revert | 恢复为此版本 |

## 8. 功能需求

### FR-01 打开知识库

- 用户可以选择现有本地目录。
- 目录可以是普通目录，也可以是现有 Git 仓库。
- 应用不移动、不复制、不转换原文件。
- 默认展示 `.md` 和 `.txt` 文件及其目录。
- `.git`、应用缓存等内部内容不出现在文档树。

### FR-02 文档与目录管理

- 支持新建 Markdown 和 TXT。
- 支持新建目录。
- 支持重命名和移动。
- 删除操作进入系统回收站；若平台不支持，则必须二次确认。
- 路径操作必须限制在知识库根目录内。
- MVP 不允许通过符号链接越过知识库根目录。

### FR-03 编辑与预览

- Markdown 使用 UTF-8。
- MVP 采用 GitHub Flavored Markdown（GFM）作为渲染基线。
- 支持源码、预览和左右分栏三种模式。
- Markdown 最低支持：标题、段落、强调、列表、任务列表、表格、引用、分隔线、代码块、链接和图片。
- P0 不渲染 Mermaid，代码块按普通代码展示。
- TXT 以纯文本编辑和预览。
- 文档预览不得反向改写源文件。

### FR-04 保存与文件监听

- 编辑内容自动保存到本地。
- 保存失败时持续显示错误状态，不能伪装为已保存。
- 应用监控知识库中的外部创建、修改、移动和删除。
- 当前文档没有本地未保存内容时，自动加载外部变化。
- 存在未保存内容时，要求用户选择保留本地、加载外部或比较两者。

### FR-05 搜索

- 支持按文件名和正文搜索。
- 结果展示文件路径和命中片段。
- 点击结果打开对应文件。
- 索引是派生数据，删除后可以自动重建。
- 性能目标：参考设备上，10,000 个中小型文本文件的普通关键词搜索中位数低于 2 秒。

### FR-06 链接和本地资源

- 支持打开标准 Markdown 相对链接。
- 支持在预览中显示知识库内部的常见图片格式。
- 链接不存在或越过根目录时明确提示。
- MVP 不提供图片裁剪、压缩或在线上传。

### FR-07 修改检查

- 展示新增、修改、删除和重命名文件。
- 支持逐行查看文本差异。
- 可以按文件恢复未提交变化。
- 恢复动作需要确认，且不能影响其他文件。

### FR-08 创建版本

- 用户可以选择要包含的文件。
- 用户必须填写版本说明，系统可提供默认建议。
- 没有变化时不能创建版本。
- 创建成功后可查看版本时间、作者、说明和文件差异。

### FR-09 团队同步

- 使用系统已有的 Git 配置和凭据。
- 支持获取远端变化和推送当前分支。
- 不执行隐式强制推送。
- 任一步骤失败都不得删除本地未提交内容。
- 断网时允许继续本地编辑，并明确显示未同步状态。

### FR-10 冲突处理

- 冲突发生后停止推送。
- 显示冲突文件列表。
- 文本冲突至少提供“本地内容”“远端内容”“手动合并”三种处理入口。
- 所有冲突解决前不允许标记同步成功。
- 解决后的内容必须再次进入修改检查。

### FR-11 版本历史与恢复

- 支持查看知识库和单文档的版本历史。
- 支持查看某版本的作者、时间、说明和差异。
- 恢复旧版本时生成新的变化或恢复 Commit。
- 不使用重写共享历史的方式恢复。

### FR-12 Agent 直接访问

- Agent 可以在应用运行或关闭时读取 `.md`、`.txt`。
- Agent 修改文件后，应用按照外部变化规则处理。
- Agent 不依赖产品数据库、私有格式或专用读取 API。
- 知识库根目录建议包含 `AGENTS.md`，声明可编辑范围、格式和 Git 规则。

### FR-13 Agent 变更审查

- Agent 修改默认发生在独立分支或未提交工作区。
- 应用能够展示 Agent 修改形成的全部文件差异。
- 用户确认前，不自动推送到受保护主分支。
- 产品不得声称能准确识别所有外部修改的真实操作者；身份以执行环境和 Git 作者信息为准。

### FR-14 语雀迁移

该功能不阻塞编辑器原型，但阻塞团队正式试点。

- 支持导入语雀导出的 Markdown 或 ZIP。
- 尽可能保留目录层级。
- 本地化 ZIP 中包含的图片并修正相对链接。
- 文件名冲突使用确定性规则处理。
- 输出迁移报告：成功、失败、重命名、远程图片、失效链接和不支持内容。
- 原始导出包只读保留，便于复核。

## 9. 推荐的团队 Git 流程

### 9.1 分支约定

- 正式知识：`main`。
- 人类修改：`docs/<user>/<topic>`。
- Agent 修改：`agent/<task-id>`。
- `main` 在远端开启保护，不允许强制推送。

### 9.2 MVP 评审方式

MVP 不自建评审系统：

1. Easy Markdown 创建版本并推送变更分支。
2. 用户在现有 GitLab、Gitea 或 GitHub 发起评审。
3. 远端负责审批和合并。
4. Easy Markdown 获取合并后的正式内容。

### 9.3 Agent 工作约定

- Agent 执行前先获取最新正式内容。
- 一个 Agent 任务对应一个独立分支。
- Agent 不操作 `.git` 内部文件。
- Agent 不执行强制推送。
- Agent 删除或批量移动文件前必须获得显式授权。
- 合并前必须由人查看差异。

## 10. 非功能需求

### NFR-01 数据安全

- 应用崩溃不能破坏已保存文件。
- 写入尽量采用临时文件加原子替换。
- 未被 Git 跟踪的新文件删除后仍应可从系统回收站恢复。
- 不在日志中记录 Git 密码、Token 或文档完整正文。

### NFR-02 边界安全

- 所有路径在读写前解析为绝对路径并验证仍位于知识库根目录。
- 防止 `../` 路径穿越。
- MVP 不跟随指向根目录之外的符号链接。

### NFR-03 可移植性

- 不安装 Easy Markdown，用户仍可用普通编辑器读取全部知识。
- 应用专属配置不得污染正文格式。
- 换行符策略应与仓库 `.gitattributes` 兼容。

### NFR-04 性能

- 文件树采用增量刷新。
- 搜索索引采用增量更新。
- 大文件需要降级策略，不能拖垮整个工作区。
- 具体规模和响应时间在技术 Spike 中确定。

### NFR-05 可观测性

- 用户能看到保存、版本和同步三个独立状态。
- 同步失败提供可执行的错误信息。
- 调试日志默认不包含敏感正文。

| 指标 | 目标 |
| --- | --- |
| 打开现有本地知识库成功率 | ≥ 99% |

| Agent 读取类任务成功率 | ≥ 95% |

## 12. 内部试点发布门槛

- P0 用户故事全部通过验收。
- 在 Windows 目标环境完成安装、升级和卸载测试。
- 完成至少一个真实语雀知识库的抽样迁移。
- 完成两人同时修改同一知识库的冲突演练。
- 完成一次 Agent 批量修改和人工回滚演练。
- 远端主分支保护已启用。
- 已知的数据损坏问题为 0。

## 13. 待决策事项

以下问题应在两周验证或技术 Spike 后决定：

1. 团队实际操作系统分布，是否允许 Windows 首发。
2. 团队使用 GitLab、Gitea、GitHub 还是其他远端。
3. MVP 是否必须在应用内完成 Git 登录。
4. 图片是直接进入 Git，还是从试点开始使用 Git LFS。
5. 知识库是一项目一仓库，还是多个项目共享一个仓库。
6. 语雀迁移采用官方导出、官方 API，还是二者结合。
7. Agent 是由 Easy Markdown 启动，还是仅操作用户已经授权的目录。
