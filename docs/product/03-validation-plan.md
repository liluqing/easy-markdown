# Easy Markdown 两周验证计划

| 字段 | 内容 |
| --- | --- |
| 文档状态 | Ready for execution |
| 版本 | 0.1 |
| 周期 | 10 个工作日 |
| 核心决策 | 是否进入正式 MVP 开发 |

## 1. 验证目标

本轮不验证界面是否精美，主要回答五个决策问题：

1. 语雀官方 MCP 当前到底能解决团队多少 Agent 场景。
2. 本地 Markdown 相比语雀 MCP 是否明显提高 Agent 的成功率、效率或可审计性。
3. 非开发人员能否接受 Git 异步协作模型。
4. 团队语雀内容能否以可接受的质量迁移。
5. 哪些功能必须进入 P0，哪些可以延后。

## 2. 待验证假设

| ID | 假设 | 通过标准 |
| --- | --- | --- |
| H-01 | Agent 直接读取本地文件比通过语雀 MCP 更稳定 | 本地方案读取任务成功率不低于 95%，且不低于语雀方案 |
| H-02 | 本地文件更适合跨文档和批量修改 | 至少一个高频任务耗时降低 30%，或人工干预明显减少 |
| H-03 | Git Diff 能降低 Agent 写入风险 | 5 名用户中至少 4 名能发现预设错误并正确撤销 |
| H-04 | 非开发用户可以使用被简化的 Git 流程 | 至少 4/5 用户无需命令行完成编辑、创建版本和同步 |
| H-05 | 语雀内容可以迁移 | 代表性文档中至少 90% 正文可用，失败内容可被报告定位 |
| H-06 | 团队可接受异步而非实时共同编辑 | 试点用户没有将实时同编列为阻塞上线的问题 |

## 3. 参与人员

建议 5～7 人：

- 1 名产品经理。
- 2 名开发人员。
- 1～2 名测试人员。
- 1 名技术负责人或架构师。
- 1 名语雀知识库管理员。

其中至少 2 人应不熟悉 Git 命令行。

## 4. 样本文档

从真实语雀知识库选择 50～100 篇文档，不使用专门为测试编写的“干净样本”。

样本至少覆盖：

- 需求文档 10 篇。
- 产品说明 10 篇。
- 技术分析或技术方案 10 篇。
- 测试用例 10 篇。
- 测试计划 5 篇。
- 其他过程文档 5 篇。

内容特征至少覆盖：

- 多级目录。
- 文档间链接。
- 图片。
- 表格。
- 任务列表。
- 代码块。
- 长文档。
- 重复文件名。
- 中文、英文和混合文件名。
- 语雀特殊块或无法直接转换的内容。

使用 [样本文档清单模板](../../research/sample-manifest.csv) 记录样本。

## 5. 对照方案

### 方案 A：语雀 + 官方 MCP

- 使用团队允许的测试空间或脱敏知识库。
- 使用范围受限的团队 Token。
- 记录 MCP 不支持、限流、权限和格式问题。
- 禁止直接在正式知识库进行破坏性写入测试。

### 方案 B：本地 Markdown + Git

验证阶段可以使用现有编辑器和 Git 工具模拟，不要求先开发完整 Easy Markdown。

- 文档保存在普通目录。
- 使用与未来产品一致的目录和分支约定。
- Agent 直接访问该目录。
- 使用 Git Diff 审查修改。
- 使用现有 Git 平台完成评审。

这可以在最低开发投入下验证核心价值，而不是验证 UI。

## 6. 任务集

### 6.1 读取类任务

| ID | 任务 | 成功定义 |
| --- | --- | --- |
| R-01 | 找到某需求的目标、范围和验收条件 | 引用正确文档，关键事实无遗漏 |
| R-02 | 汇总某功能涉及的产品、技术和测试文档 | 找到至少 90% 的标准答案文档 |
| R-03 | 找出两个文档中的冲突描述 | 正确指出冲突位置和内容 |
| R-04 | 根据需求生成一页技术分析摘要 | 事实正确，不虚构不存在的接口 |
| R-05 | 回答一个需要跨 5 篇以上文档的问题 | 输出可追溯到来源文件 |

### 6.2 写入类任务

| ID | 任务 | 成功定义 |
| --- | --- | --- |
| W-01 | 根据需求变更更新一组测试用例 | 修改范围正确，未破坏无关内容 |
| W-02 | 新建一篇技术分析文档 | 路径、文件名和结构符合约定 |
| W-03 | 批量替换过期产品名 | 目标命中完整，代码示例和历史引用按规则保留 |
| W-04 | 给多篇文档补充负责人和状态元数据 | Front Matter 合法，正文不变 |
| W-05 | 重组一个目录并修复相对链接 | 目录正确，内部链接没有新增失效 |

### 6.3 协作与恢复任务

| ID | 任务 | 成功定义 |
| --- | --- | --- |
| C-01 | 两名成员修改不同文档后同步 | 自动合并并保持双方内容 |
| C-02 | 两名成员修改同一行后同步 | 正确进入冲突状态，不静默覆盖 |
| C-03 | Agent 错误删除一段内容 | 用户能从 Diff 中发现并恢复 |
| C-04 | Agent 错误修改多个文件 | 用户能一次查看全部影响并撤销 |
| C-05 | 断网编辑后恢复联网同步 | 本地内容保留，状态表达清楚 |

### 6.4 迁移任务

| ID | 任务 | 成功定义 |
| --- | --- | --- |
| M-01 | 导出并导入一个代表性语雀知识库 | 目录、正文和大部分图片可用 |
| M-02 | 检查迁移后的内部链接 | 失效链接被修复或进入报告 |
| M-03 | 检查特殊块和无法转换内容 | 不静默丢失，全部进入迁移报告 |
| M-04 | 比较迁移前后抽样文档 | 关键业务信息没有缺失或误改 |

## 7. 质量评分规则

每次任务由执行人和复核人分别评分。

| 分数 | 定义 |
| --- | --- |
| 5 | 完全正确，可直接使用 |
| 4 | 仅需少量措辞或格式调整 |
| 3 | 主体正确，但需要明显人工修订 |
| 2 | 只完成一部分，存在重要遗漏或错误 |
| 1 | 基本不可用 |
| 0 | 未完成、数据损坏或产生不可接受风险 |

任务成功定义：

- 质量评分至少为 4。
- 没有不可恢复的数据损坏。
- 没有越权读取或写入。
- 人工干预次数和耗时被完整记录。

## 8. 记录字段

每次执行使用 [验证结果记录模板](../../research/validation-results.csv)，至少记录：

- 参与人角色。
- 对照方案。
- 任务 ID。
- 完成与否。
- 总耗时。
- Agent 执行次数。
- 人工干预次数和耗时。
- 质量评分。
- 是否发生格式损坏。
- 是否发生越权或安全问题。
- 是否可通过差异发现错误。
- 是否成功恢复。
- 主要问题和用户反馈。

## 9. 十个工作日安排

### 第 1 天：启动

- 确认参与人员。
- 冻结任务集和评分规则。
- 确认测试数据的脱敏和权限要求。
- 收集团队操作系统和 Git 平台信息。

### 第 2 天：样本选择

- 完成 50～100 篇样本文档清单。
- 标记特殊块、图片、链接和敏感级别。
- 建立迁移前基准截图或核验记录。

### 第 3 天：语雀 MCP 基线

- 在受控空间配置官方 MCP。
- 验证读取、搜索、新建和修改能力。
- 执行 R-01～R-05。

### 第 4 天：语雀写入基线

- 执行 W-01～W-05。
- 记录 Token 权限、限流、格式和审查问题。
- 恢复所有测试写入。

### 第 5 天：本地工作流搭建

- 将样本迁移到本地目录。
- 初始化 Git 和远端测试仓库。
- 配置主分支保护和分支命名。
- 准备 Agent 工作目录规则。

### 第 6 天：本地 Agent 测试

- 执行 R-01～R-05 和 W-01～W-05。
- 记录速度、质量、批量修改和来源追踪情况。

### 第 7 天：团队协作测试

- 执行 C-01～C-05。
- 观察非开发用户是否需要命令行或开发人员协助。

### 第 8 天：迁移复核

- 执行 M-01～M-04。
- 统计正文、图片、链接和特殊内容的迁移质量。

### 第 9 天：用户访谈

- 每位参与者进行 20～30 分钟访谈。
- 汇总阻塞问题、价值点和不需要的功能。
- 标记 P0 范围调整建议。

### 第 10 天：决策评审

- 比较语雀 MCP 和本地方案。
- 逐项判断 H-01～H-06。
- 作出 Go、Conditional Go 或 No-Go 决策。
- 若继续，冻结 PRD 0.2 和技术 Spike 范围。

## 10. 用户访谈提纲

1. 哪个任务最能体现本地知识库的价值？为什么？
2. 哪一步最难理解或最容易出错？
3. 如果继续使用语雀 MCP，你还缺少什么？
4. 你是否愿意放弃同一文档的实时共同编辑？在什么条件下可以？
5. 你能否理解“保存、创建版本、同步”的区别？
6. Agent 修改后，你最希望看到哪些信息才敢接受？
7. 发生冲突时，你希望自己处理还是交给指定管理员？
8. 哪类语雀内容迁移失败会阻止你切换？
9. 如果明天必须使用该方案工作，你认为最缺少的三个功能是什么？
10. 你更担心数据丢失、信息泄露、操作复杂，还是协作效率下降？

## 11. 决策规则

### Go

- 所有硬性立项门槛通过。
- 本地方案相对语雀 MCP 存在明确高频优势。
- 没有无法缓解的数据安全或迁移风险。

### Conditional Go

- 核心价值成立，但迁移、冲突或非开发用户体验有明确缺口。
- 缺口可以通过一个受限 P0 范围在 2～4 周内验证。

### No-Go

- 语雀 MCP 已满足绝大多数场景，本地方案没有明显收益。
- 迁移质量无法达到最低要求。
- 团队强依赖实时共同编辑。
- 非开发人员无法接受 Git 异步协作模型。
- Agent 写入无法达到团队要求的安全边界。

## 12. 验证结束时的交付物

- 完整验证结果 CSV。
- 语雀 MCP 与本地方案对比报告。
- 迁移问题清单和成功率。
- 用户访谈纪要。
- 更新后的 MVP PRD 0.2。
- Go / Conditional Go / No-Go 决策记录。
- 若继续：技术 Spike 清单和原型验收范围。
