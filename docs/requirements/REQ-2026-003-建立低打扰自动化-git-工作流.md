# REQ-2026-003：建立低打扰自动化 Git 工作流

## 1. 问题与证据

现有仓库规则要求每个任务分别明确授权 commit、push、PR 和 merge。即使变更目标和边界
已经清晰，Agent 仍会在完成阶段重复询问，打断用户并把 Git 流程负担暴露给普通成员。

用户在 2026-07-18 明确要求设计仓库级 Git 工作流：常规安全动作应按长期规则自动推进，
只在真正需要决定或存在风险时询问。只读检查同时确认当前仓库没有提交、远端、CI 或分支
保护，当前 `master` 上的全部文件均未跟踪，因此本次不能把现有文件自动视为已授权基线。

## 2. 目标用户与预期结果

- 目标用户：使用自然语言协作的开发、产品、测试成员，以及执行仓库任务的 Agent。
- 预期结果：一次“做/修/实现”授权覆盖该 WORK 的常规 Git 生命周期，Agent 不再逐次询问
  branch、commit、push、Draft PR 或满足保护条件后的 merge。
- 可观察的成功信号：安全路径自动完成；只有冲突、文件归属、秘密、失败闸门、远端/身份、
  分支保护或高风险动作等例外会暂停并提出一个最小问题。

## 3. 范围

- Trunk-Based：受保护的 `main`、短生命周期任务分支和 PR 合入。
- Agent 分支命名、同步、精确暂存、检查点提交、交接点推送和提交信息规范。
- 首次推送后自动维护 Draft PR，质量闸门通过后转为 Ready。
- CI、非作者批准、风险和分支保护均满足时自动 Squash Merge。
- 明确长期授权、必须询问、禁止自动执行和失败恢复矩阵。
- 提供机器可读 Git 策略，持久化 bootstrap 模式、canonical 远端、refspec、敏感路径、文件
  阈值、全部 CODEOWNERS 位置、URL rewrite/scheme、required checks、未评审分支 CI 无特权
  边界和 merge 能力，并阻止旧分支或候选治理规则绕过当前主干规则。
- 将规则接入根约束、Harness Skill、开发流程、质量闸门、交接与成员指南。
- 让 Harness 检查必需 Git 工作流文档，并进行独立 Agent 前向测试。

## 4. 非目标

- 不改变 Easy Markdown 产品内面向知识库用户的 Git 功能设计。
- 不选择 Git 托管供应商，不配置远端、凭据、CI、分支保护或托管平台规则。
- 不在本次创建初始提交、推送、PR 或合并；当前无可信已提交基线和远端。
- 不自动强制推送、重写共享历史、绕过质量/审批、发布、部署或创建发布标签。
- 不把诊断、评审或“先别改”解释为 Git 写入授权。

## 6. 约束、依赖与风险

- 产品约束：用户用自然语言表达目标，Git 治理是 Agent 后台机制。
- 技术依赖：自动 push/PR/merge 只在远端、凭据、托管集成、CI 和保护规则真实存在时可用。
- 远端执行约束：未评审分支代码及 CI 间接执行代码不得获得生产秘密、可写/高权限 token
  或持久化凭据；外部 action/workflow/include 必须不可变固定。
- 数据/隐私/安全：只暂存当前 WORK 拥有的路径；提交前检查秘密、异常大文件、二进制和
  无关差异。任何可疑项先停止，不把内容上传到远端。
- 兼容与迁移：当前是无提交、无远端的 unborn `master`；新规则从仓库完成独立 bootstrap
  后生效，本次不重命名分支或导入基线。
- 回退考虑：流程文档可通过后续 REQ 修改；已经推送或合并的共享历史不得用强制操作回退。

## 7. 方案边界

一次明确的变更授权构成该 WORK 常规 Git 动作的长期授权，但不得扩大到任务外文件或外部
发布。Agent 在每个单一意图且相关检查通过的恢复点自动 commit；只在暂停、交接或 PR-ready
时 push。首次 push 自动创建/更新 Draft PR，满足全部保护条件后自动 Squash Merge。

本需求只替代 [REQ-2026-002](REQ-2026-002-支持口语化意图理解与-grilling-决策澄清.md)
中“软件仓库常规 commit/push/PR/merge 必须逐项显式授权”的部分；发布、删除、迁移、高风险
例外和产品内 Git 行为仍保留原有明确授权边界。

自动 fetch 和安全 fast-forward 可以执行；分叉、冲突、非快进拒绝或共享历史改写不得
自动解决。低打扰不等于隐藏失败：所有跳过、失败和必要询问必须写入 WORK 交接。

## 8. 验收标准

- [x] AC-1：清晰的实现请求会自动获得必要的轻量 WORK、聚焦分支、检查点 commit、交接点
  push 和 Draft PR，Agent 不再为这些常规动作逐次询问。
- [x] AC-2：工作流以受保护 `main` 为主干；Agent 分支从 exact base SHA 创建并验证 ancestry，
  标准分支包含 `codex/` 与 WORK ID，无 WORK 的轻微变更也可追踪。
- [x] AC-3：WORK 记录 owned paths/初始状态；预脏文件整文件受保护，自动 commit 只暂存
  clean/absent 起始的任务路径或可证明的纯 Agent patch，并通过差异、秘密、异常文件和检查。
- [x] AC-4：push 仅发生在暂停、交接或 PR-ready；首次 push 自动维护 Draft PR；只有 `done`
  且归档、归档后 Harness 通过的 WORK 可转 Ready，`abandoned` 永不 Ready/merge。
- [x] AC-5：只有轻微/标准变更在 changed-files、CI、非作者批准、风险证据、有效主干保护和
  expected-head 原子 merge 全部绑定 exact HEAD，且分支点 base、当前 protected tip、候选
  HEAD 的规则取最严格交集时才自动 Squash Merge；重大/紧急永不自动。
- [x] AC-6：工作流列出必须询问的例外；秘密硬阻断；CI/评审等待不询问；候选治理/远端执行
  规则不能自我授权；未评审分支 CI 保持无生产秘密/高权限；强制推送、共享历史重写、安全
  绕过、发布、部署和标签不属常规授权；任何网络访问前解析所有 URL/rewrite/多值端点并
  匹配机器策略。
- [x] AC-7：当前无提交/远端仓库被识别为 bootstrap 例外，本次不创建初始提交或远端状态。
- [x] AC-8：机器 Git 策略校验 bootstrap/active 信任边界、所有 CODEOWNERS 位置、URL
  rewrite/scheme、敏感路径、文件阈值、CI 无特权与 merge 能力；根规则、团队文档、Harness
  Skill 和检查脚本一致，校验及独立 Agent 前向测试通过。

每条标准必须能独立判断通过或失败，并在 WORK 中关联证据。

## 9. 验证计划

- 自动化：运行 Harness 检查、Skill 结构校验、脚本语法检查和占位符扫描。
- 人工验证：逐项审查 Git 动作/授权矩阵与现有文件安全规则是否矛盾，并由独立 Agent
  复核权限、远端执行和终态漏洞。
- 测试数据/环境：独立 Agent 处理一个普通实现完成场景和一个包含非任务文件/冲突的场景；
  再验证主干收紧规则与 abandoned 终态；不执行真实 Git 写入或远端操作。
