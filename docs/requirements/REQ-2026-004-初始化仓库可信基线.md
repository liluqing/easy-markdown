# REQ-2026-004：初始化仓库可信基线

## 1. 问题与证据

仓库已经存在 `.git`，但仍是 unborn `master`：没有 HEAD、提交、上游或远端，全部 51 个
既有文件均未跟踪。现有 Git 工作流因此处于 `bootstrap-limited`，无法把 Harness、产品、
技术和调研真源作为可恢复的可信基线。

只提交狭义 Harness 文件会遗漏其链接闭包中的产品、技术、ADR 和调研文件，使当前脏工作区
检查看似通过、但 clean checkout 出现断链。只读审计确认完整闭包恰好是当前全部 51 个文件。

## 2. 目标用户与预期结果

- 目标用户：维护 Easy Markdown 的团队成员和无聊天记忆的 Agent。
- 预期结果：建立完整、可验证、无秘密的本地初始 Git 基线，并把默认主干统一为 `main`。
- 可观察的成功信号：根提交无父提交且 tree 等于批准清单；终态证据另有聚焦提交；最终
  `main` 工作区干净、Harness 通过，远端阶段准确标记 `not-run`。

## 3. 范围

- 当前除 `.git` 外的全部 51 个既有文本文件。
- 本需求和 `WORK-2026-004`。
- 新增 `.gitignore`、`.gitattributes`，并让初始提交中的文本统一为 LF。
- 将 unborn `master` 重命名为 `main`。
- 使用已有 Git 身份 `liluqing <liluqing@fshows.com>` 创建一个原子根提交。
- 根提交成功后，把准确 SHA 和验证写回 REQ/WORK，归档 WORK，再创建一个聚焦终态提交。

## 4. 非目标

- 不配置或接触远端，不 fetch、push、创建 PR、运行远端 CI 或 merge。
- 不启用 `git-policy.json` 的 `active` 模式，不配置 canonical repository、checks 或保护规则。
- 不发布、部署、创建标签、重写历史或拆分猜测不存在的“前 Harness 历史”。
- 不把根提交拆成产品、技术和 Harness 的伪历史。

## 6. 约束、依赖与风险

- 产品约束：Markdown/TXT/普通文件仍是知识与治理真源；初始化不得改变产品功能。
- 技术依赖：系统 Git 和现有 Harness 脚本；不新增运行时依赖。
- 数据/隐私/安全：提交前复核秘密、个人数据、文件大小、二进制、符号链接和异常文件；
  只按最终清单显式暂存，不使用 `git add .`、`git add -A` 或通配符。
- 兼容与迁移：全局 `core.autocrlf=true`；使用 `.gitattributes` 固定仓库文本为 LF。
- 回退考虑：提交前可安全停止且不改写历史；根提交成功后不得用 reset/rebase/force 隐藏
  结果，若验证失败则保留证据并用后续提交修复。

## 7. 方案边界

这是 [Git 工作流](../harness/git-workflow.md) 定义的一次性 bootstrap 例外。根提交直接建立
unborn `main`，不创建普通 `codex/WORK-*` 分支；该例外只授权已确认的初始清单和两个聚焦
提交，不扩大到远端或后续常规 Git 自动化。

初始根提交使用：

```text
chore(harness): establish initial repository baseline

Work: WORK-2026-004
Req: REQ-2026-004
```

终态提交只保存根 SHA、验证、REQ 状态和归档 WORK，不与根提交混淆。

## 8. 验收标准

- [x] AC-1：初始清单覆盖 51 个既有文件、本 REQ、WORK、`.gitignore` 和 `.gitattributes`；
  所有候选均通过 UTF-8、秘密、大小、二进制、链接和异常文件检查。
- [x] AC-2：unborn 分支改为 `main`，根提交无父提交且提交 tree 与批准清单完全一致。
- [x] AC-3：根提交标题和 `Work`/`Req` trailers 正确，作者身份使用已配置值。
- [x] AC-4：根提交后 Harness、脚本语法、提交内容和工作区状态验证通过，准确 SHA 写入 WORK。
- [x] AC-5：REQ 变为 `validated`、WORK 变为 `done` 并归档，终态证据通过第二个聚焦提交保存。
- [x] AC-6：最终 `main` 工作区干净；没有 remote/upstream/push/PR/CI/merge/tag，策略仍为
  `bootstrap-limited`。

每条标准必须能独立判断通过或失败，并在 WORK 中关联证据。

## 9. 验证计划

- 自动化：Harness、全部 Harness `.mjs` 语法、UTF-8/换行、秘密形态、文件大小/类型、
  staged manifest、cached diff、根提交父数、tree manifest、最终 status/log。
- 人工验证：审查最终暂存清单、提交消息、REQ/WORK 证据与远端 `not-run` 状态。
- 测试数据/环境：当前 Windows 工作区和系统 Git；不进行网络访问。
