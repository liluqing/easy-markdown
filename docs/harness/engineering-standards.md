# 工程规范与开发原则

本文件描述长期工程判断。精确技术选择和系统结构以
[MVP 技术选型与架构](../technical/02-technology-selection.md) 及
[ADR](../technical/adr/README.md) 为准。

## 1. 文件优先与可恢复

- Markdown、TXT 和本地资源文件是知识正文的唯一真源。
- 索引、缓存、派生视图和应用状态必须可以删除后重建。
- 写入采用边界校验、版本令牌和安全替换；绝不静默覆盖外部变化。
- 恢复通过新变更完成，不改写共享 Git 历史。

## 2. 明确信任边界

- React/WebView 只负责展示和交互，不直接访问任意文件或执行任意系统命令。
- Rust Core 拥有工作区注册、路径解析、文件 I/O、监听、Git、搜索和本地资源访问。
- 所有传入路径先规范化，再证明位于已授权工作区内；符号链接与大小写差异纳入测试。
- Git 与 ripgrep 参数从类型化允许列表构造，不接受前端传入原始参数数组。
- Markdown 不执行原始 HTML、远程脚本或危险 URL；远程图片默认不自动加载。
- 日志记录操作、耗时和稳定错误码，不记录文档正文、Token、凭据或敏感绝对路径。

## 3. 单向依赖与单一规则

- UI feature 可以依赖共享 contracts，contracts 不依赖 UI。
- Rust 命令层只做输入/输出适配，业务规则位于对应领域模块。
- 前端不能复制路径、文件保存、Git 或权限规则来“提前判断”；后端返回稳定结果。
- 同一状态机只实现一份，并用测试覆盖转换与失败路径。
- 跨边界结构显式版本化；改变字段语义时同时更新两端与兼容测试。

## 4. 最小完整变更

- 以验收标准为边界，交付能独立验证的最小切片。
- 不为假想未来建立通用框架；第二个真实用例出现后再提炼复用。
- 优先标准库和已有依赖。新增运行时依赖须说明维护性、安全、许可证、体积和替代方案。
- 不在 Bug 修复中夹带重构；必要重构要么是修复所需的最小部分，要么独立成 WORK。
- 保持清晰命名和小接口；注释解释“为什么”，不复述代码。

## 5. 错误、并发与取消

- IPC 使用稳定、可测试的错误码；面向用户的文案与底层错误细节分离。
- 文件保存、同步、搜索等长操作拥有 operation ID，并能报告进度、超时和取消。
- 预期版本不一致时返回冲突，不自动选择任一方。
- 部分成功必须显式返回逐项结果；不能用一个成功布尔值隐藏失败文件。
- 失败路径与恢复路径和成功路径同等重要，至少有单元或集成测试。

## 6. 安全与隐私

- 默认最小权限，只授权用户选择的工作区。
- 新协议、CSP 例外、外部进程、远程资源和持久化字段都视为安全边界变化。
- 任何遥测、崩溃上报或远程请求必须另有明确需求，MVP 不默认采集。
- 测试夹具使用虚构数据；调研材料提交前脱敏。
- 不把凭据写进配置、日志、快照、测试或文档示例。

## 7. 测试设计

- 单元测试覆盖纯规则、状态机、解析和错误映射。
- Rust 集成测试使用临时目录和临时 Git 仓库覆盖真实文件行为。
- 前端组件测试覆盖关键交互、可访问性和错误状态，不只检查快照。
- E2E 覆盖人类编辑、外部 Agent 修改、版本创建、冲突和恢复等核心闭环。
- 安全回归测试覆盖路径越界、恶意 Markdown、任意命令参数和敏感日志。
- 性能目标使用可复现数据集和统计结果，不凭主观感受宣称通过。

## 8. 可访问性与产品语言

- 键盘操作、焦点、对话框和菜单遵循通用可访问模式。
- Git 概念在产品 UI 中使用 PRD 定义的用户语言，底层代码可保留准确 Git 术语。
- 错误提示说明发生了什么、数据是否安全以及用户下一步，不只展示 stderr。
- 中文输入法、中文路径、空格、Unicode 和 Windows 路径是首发必测场景。

## 9. 可逆与可观察

- 高风险变化先提供回退方案或特性开关，再扩大范围。
- 迁移不得就地破坏唯一副本；保留来源、报告成功与失败并支持复核。
- 关键操作记录结构化事件和关联 operation ID，便于定位但不泄露正文。
- 无法观察或复现的“偶发成功”不算完成。
