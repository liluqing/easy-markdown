# 文档治理

文档治理的核心不是增加文件数量，而是让每种事实只有一个主人，并规定事实变化时谁必须
更新什么。

## 1. 目录职责

| 路径 | 内容 | 生命周期 |
| --- | --- | --- |
| `README.md` | 项目目的、当前阶段、主要入口 | 每次阶段变化更新 |
| `AGENTS.md` | 仓库范围的强制协作规则 | 规则变化时评审 |
| `docs/product/` | 当前产品基线、PRD、用户故事、验证计划 | 产品行为变化时更新 |
| `docs/requirements/` | 单次变化的原因、范围、验收和决策记录 | 永久保留，可 supersede |
| `docs/work/active/` | 当前执行状态和跨会话交接 | 工作中持续更新 |
| `docs/work/archive/` | 完成或放弃工作的证据 | 只追加修正，不当当前真源 |
| `docs/technical/` | 当前技术基线、架构、Spike | 技术边界变化时更新 |
| `docs/technical/adr/` | 长期技术决策的背景、取舍和后果 | 永久保留，可 supersede |
| `docs/harness/` | 开发流程、原则、质量和治理 | 流程变化时更新 |
| `docs/templates/` | REQ、WORK、ADR 的标准骨架 | 字段规则变化时更新 |
| `research/` | 原始调研、实验数据和来源 | 保留证据，敏感信息先脱敏 |

## 2. 文档之间的边界

- 产品基线回答“系统当前应该怎样”；REQ 回答“为什么要发生这次变化”。
- REQ 拥有范围与验收；WORK 只引用它，并拥有计划、进度、证据和交接。
- ADR 回答“为什么选择这个长期技术方向”；技术基线描述接受决定后的当前系统。
- `docs/harness/git-workflow.md` 拥有软件仓库的 branch、commit、push、PR、merge 和询问边界；
  `git-policy.json` 持久化可机器检查的远端信任、敏感路径、阈值和保护能力。产品内知识库
  Git 行为仍由产品/技术基线和 ADR 拥有。
- 调研数据支持结论，但不自动成为决策；决策必须回写 REQ、产品文档或 ADR。
- Git 历史保存版本，不手工复制 `v1-final-final` 文件。

## 3. 状态词表

REQ 只能使用：

| 状态 | 含义 |
| --- | --- |
| `proposed` | 正在澄清，尚未授权实现 |
| `accepted` | 已批准且达到 Ready |
| `in-progress` | 已有 active WORK 执行 |
| `validated` | 验收条件已验证，尚未代表发布 |
| `released` | 已进入目标发布或团队正式流程 |
| `rejected` | 明确不做，并保留原因 |
| `superseded` | 被另一 REQ 替代，并链接替代项 |

WORK 只能使用：

| 状态 | 含义 |
| --- | --- |
| `planned` | 已建立但未开始 |
| `in-progress` | 正在执行 |
| `blocked` | 需要外部决定或条件 |
| `review` | 实现完成，等待评审/验收 |
| `done` | 验收通过，可归档 |
| `abandoned` | 明确停止，已写明原因，可归档 |

ADR 沿用 [ADR 索引](../technical/adr/README.md) 中的状态。产品和技术基线在现阶段沿用
文档顶部状态表；新增自动化前不批量改写历史文档格式。

## 4. 更新触发器

| 发生的变化 | 必须检查或更新 |
| --- | --- |
| 用户可见行为、范围或验收变化 | REQ、产品基线、用户故事、测试 |
| 产品架构、依赖、IPC、数据、安全或产品内 Git 行为变化 | REQ、ADR、技术基线、安全/集成测试 |
| 软件仓库 Git 协作或授权变化 | REQ、AGENTS、Git 工作流、Harness Skill、质量/交接规则 |
| 项目阶段或主要入口变化 | README |
| 开发流程、状态、质量要求变化 | AGENTS、Harness、模板、校验脚本 |
| 执行计划、阻塞、风险、验证或下一步变化 | active WORK |
| Spike 或研究得到结论 | 原始证据、关联 REQ/ADR、相应基线 |
| 文件移动或重命名 | 所有入站链接与 Harness 检查 |

## 5. 链接与命名

- 使用仓库内相对链接，使 Git 平台和本地预览都能工作。
- REQ 文件名为 `REQ-YYYY-NNN-<slug>.md`。
- WORK 文件名为 `WORK-YYYY-NNN-<slug>.md`。
- ADR 文件名为 `NNNN-<slug>.md`，标题为 `ADR-NNNN`。
- ID 一旦创建不复用；重命名标题时保留 ID。已创建的记录不得删除，生成器以仓库中
  保留的最大 ID 继续分配，并在三/四位容量耗尽时明确失败。
- 链接到标题可能变化的文档时优先链接文件；需要精确位置时再使用稳定章节锚点。
- 不把本机绝对路径、临时目录或聊天链接写成长期依赖。

## 6. 编码与换行

- 文本文件统一使用 UTF-8 和 LF，以根目录 `.editorconfig` 为准。
- Node Harness 明确按 UTF-8 读写，并兼容 frontmatter 开头的 UTF-8 BOM。
- Windows PowerShell 5.1 读取中文时使用 `Get-Content -Encoding UTF8`；默认
  `Get-Content` 可能按 GBK 显示乱码，但不代表文件损坏。
- 不为修复显示问题批量转换用户文件编码；编码迁移需要独立 REQ/WORK 和备份。

## 7. 冲突、过期与替代

- 两个真源看似冲突时，先按它们拥有的事实类型区分；仍冲突则建立/更新 WORK 处理。
- 不静默删除历史需求或 ADR。使用 `rejected`/`superseded` 并链接原因和替代项。
- 已归档 WORK 不是当前计划；若继续开发，创建新 WORK 并链接旧项。
- 发现过期内容时，先修正拥有该事实的文档，再修正引用者。
- Agent 不根据日期自动认定内容失效；只有新的已接受事实能替代旧事实。

## 8. 调研和敏感数据

调研材料必须记录来源、采集日期、负责人、用途和限制。提交前删除或替换个人信息、凭据、
私有 URL 和真实客户内容。详细要求见 [调研数据治理](../../research/README.md)。
