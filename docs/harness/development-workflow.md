# 开发流程

本流程覆盖产品需求、Bug、技术改进、文档与仓库治理变化。目标是让每次变更都可以恢复，
同时避免为轻微修改制造不必要的文档。

## 1. 变更分类

### 轻微变更

同时满足以下条件：

- 不改变用户可见行为、接口、数据、依赖、架构或安全边界。
- 修改范围小且风险显而易见，例如错字、失效链接或措辞澄清。
- 不需要跨会话规划。

轻微变更不要求 REQ；只要进入自动 commit/PR 生命周期，就由 Agent 后台建立
`requirement: none` 的轻量 WORK，以保存初始文件归属、验证和 Ready 证据。只有用户明确
要求本地、不提交且同会话完成的轻微编辑可省略 WORK；仍须保护用户改动、检查差异和验证。

### 标准变更

包括用户可见行为、Bug 修复、测试行为变化或多文件实现。必须有已接受的 REQ 和一个
active WORK。

### 重大变更

包括架构、运行时依赖、信任边界、数据格式、IPC、Git 行为或团队开发流程变化。必须有
REQ 与 WORK；影响产品技术架构时还需要 ADR。

### 紧急变更

只用于数据丢失、安全暴露或阻断性故障。可以先创建 WORK 进行止损，但合并前必须补齐
需求边界、回归测试、验证证据和复盘。紧急不等于免除流程。

## 2. 阶段一：接收与澄清

1. 从用户的自然语言判断当前要探索、诊断、规划、变更、评审还是恢复；用户不需要填写
   Harness 模板或说出内部状态。
2. 搜索现有 PRD、用户故事、REQ、WORK、ADR、代码和环境事实，避免把可发现信息反问
   用户，也避免重复建档。
3. 判断信息是否足够：
   - 清晰且低风险：采用可逆的推荐假设并继续。
   - 存在高影响未决决定：进入 `$grilling`，按依赖顺序一次只问一个问题；最终共同理解
     确认前保持只读。
4. 共同理解足够后，由 Agent 在后台用需求生成器建立 `proposed` REQ。
5. 写清：
   - 问题和证据。
   - 目标用户与预期结果。
   - 范围和非目标。
   - 验收标准。
   - 风险、依赖和验证方式。
6. 链接受影响的 FR/US，不复制整份产品文档。
7. 由有授权的产品/项目负责人决定接受、拒绝或要求补充。其清晰自然语言指令可以构成
   接受，不要求说出 `accepted`；Agent 必须记录解释依据，不能自行批准含糊决定。

需求未达到 [Definition of Ready](quality-gates.md#1-definition-of-ready) 时不得进入标准
实现；技术 Spike 可以作为需求就绪前的发现工作，但必须明确它不承诺交付功能。

完整的口语解释、授权边界和 Grilling 触发条件见
[用户与 Agent 的自然语言协作协议](user-agent-interaction.md)。

## 3. 阶段二：计划

1. 确认没有相同 active WORK。
2. 从已接受的 REQ 创建一个 WORK。
3. 记录 Git 状态和必须保护的已有用户改动。
4. 有可信已提交基线、exact base SHA 和 active 策略时，按
   [Git 工作流](git-workflow.md) 自动创建或恢复聚焦分支；远端暂时不可用只阻断远端阶段。
   处于 bootstrap 受限模式时记录原因，不把全部未跟踪文件自动纳入基线。
5. 链接相关产品/技术文档与 ADR。
6. 将验收标准拆成可验证步骤，标出高风险假设。
7. 判断是否需要 ADR、原型、迁移/回退方案或安全评审。
8. 把 WORK 状态从 `planned` 改为 `in-progress`。

一个 WORK 应是可独立评审的最小完整切片。若范围需要分给多个成员，为每个可独立交付的
切片建立 WORK，并在 REQ 中关联它们。

## 4. 阶段三：实施

- 只修改当前 WORK 范围内的文件；发现邻近问题时记录后续需求，不顺手扩张。
- 优先遵循现有目录与模块模式，新增抽象或依赖前说明当前收益。
- 每次重要决定、范围变化、阻塞、风险或下一步改变后更新 WORK。
- 先写明契约和失败行为，再实现跨前后端 IPC、持久化或 Git 操作。
- 重大技术选择先形成 Proposed ADR，再让实现成为验证证据。
- 测试与文档随实现同步更新，不留到最后凭记忆补写。

若验收标准必须改变，停止当前实现：先更新 REQ 的范围和决策记录，由负责人重新确认，
再同步 WORK。Agent 不能把“实现更方便”当作需求变更授权。

## 5. 阶段四：验证

1. 逐条映射验收标准与证据。
2. 根据风险运行格式、类型、单元、集成、E2E、安全和人工平台检查。
3. 执行 `node scripts/harness/check-harness.mjs`。
4. 在 WORK 中记录准确命令、结果、时间和未运行项；失败不得写成通过。
5. 检查完整差异，排除无关变化、秘密、调试输出和未解析模板。

测试选择矩阵见 [质量闸门](quality-gates.md)。

## 6. 阶段五：评审与关闭

评审至少回答：

- 变化是否仍符合 REQ 的目标、范围和非目标？
- 每条验收标准是否有可复核证据？
- 是否保持技术边界和安全默认值？
- 是否遗漏产品基线、技术基线或 ADR 更新？
- 是否能安全回退，是否引入未说明的兼容风险？
- WORK 是否足以让下一位成员恢复？

通过后：

1. 更新当前产品/技术真源，而不是只在 WORK 中描述新事实。
2. 将 REQ 更新为 `validated`；实际发布后再改为 `released`。
3. 完成 WORK 交接段，状态改为 `done`。
4. 使用归档脚本移入 `docs/work/archive/`。
5. 对归档后的最终状态重新运行 Harness 检查；只有该结果通过才满足 DoD。
6. 按 Git 工作流创建最终检查点、push/更新 PR，并在 exact HEAD 满足全部闸门后进入 Ready。

归档变更进入最终分支检查点并按 Git 工作流 push/更新 PR；随后 Ready、审批、自动合并和
实际 merge 状态由托管平台拥有。merge 不反过来要求再创建一个“关闭 WORK”提交。

放弃的工作走独立终态：写明原因、保留结果、未满足验收、残余风险和后续负责人，状态改为
`abandoned` 后归档，再对归档状态运行 Harness。它不满足 DoD，不得把 PR 转为 Ready 或
merge；远端只可保留/关闭 Draft 交接证据。

## 7. Git 协作

完整规则见 [软件仓库 Git 工作流](git-workflow.md)。一次清晰实施授权覆盖当前 WORK 的
常规 Git 生命周期，不需要逐次确认：

1. 自动创建或恢复包含 WORK ID 的短生命周期分支。
2. 单一意图且提交闸门通过时，显式暂存任务路径并自动 commit。
3. 暂停、交接或 PR-ready 时自动 push，并创建/更新 Draft PR。
4. `done` 且归档后，Definition of Done 对 exact HEAD 通过才转为 Ready；`abandoned` 永不
   Ready/merge。分支点 base、当前 protected tip 与候选规则取最严格交集，CI、非作者批准、
   无高风险标记和主干保护全部可验证时才自动 Squash Merge。

Agent 只在文件归属/秘密、失败闸门、远端/身份、非快进/冲突或保护条件不足等例外阻塞
当前目标时询问。诊断/评审/方案不触发 Git 写入；用户显式“不要提交/推送”优先。强制
推送、共享历史重写、发布、部署和标签不属于常规授权。

Easy Markdown 产品面向知识库用户的分支规则仍由
[MVP PRD](../product/02-mvp-prd.md) 定义，本节只约束本软件仓库本身。
