# 质量闸门

质量闸门按风险选择，不要求每次变更运行所有测试；但任何未运行的相关检查都必须记录
原因和残余风险。

## 1. Definition of Ready

标准或重大变更开始实施前，REQ 必须满足：

- [ ] 问题、证据和目标用户明确。
- [ ] 预期结果可观察，范围和非目标明确。
- [ ] 验收标准可独立判断通过或失败。
- [ ] 受影响的产品文档、技术边界和现有需求已链接。
- [ ] 依赖、数据、安全、迁移和兼容风险已识别。
- [ ] 验证方式和所需测试数据已说明。
- [ ] 负责人明确，授权人员的接受决定已留痕并反映为 `accepted`；清晰自然语言指令可以
  作为决定依据，不要求用户说出状态名。

WORK 开始前还必须满足：

- [ ] 没有重复 active WORK。
- [ ] 已记录当前 Git 状态和要保护的用户改动。
- [ ] 计划覆盖每条验收标准。
- [ ] 已判断是否需要 ADR、Spike、回退或安全评审。

## 2. Definition of Done

- [ ] REQ 的每条验收标准都有实现或验证证据。
- [ ] 与风险相称的测试通过，命令与结果已记录。
- [ ] 失败、取消、并发、冲突和恢复路径得到相称验证。
- [ ] 用户可见变化已更新产品基线；技术变化已更新技术基线/ADR。
- [ ] 新依赖、配置、数据格式和安全影响均已评审。
- [ ] 完整差异已检查，没有秘密、调试文件、占位符或无关变化。
- [ ] Git 生命周期已按 [软件仓库 Git 工作流](git-workflow.md) 推进到当前条件允许的最高安全
  阶段；bootstrap/远端/保护限制准确记为 `not-run`，实际 merge 不作为 DoD 前置条件。
- [ ] WORK 的交接字段完整，剩余风险和未验证项没有被隐藏。
- [ ] WORK 状态为 `done` 并已移入 archive。
- [ ] 归档后的最终仓库状态通过 `node scripts/harness/check-harness.mjs`。

“代码已经写完”不等于 Done；“测试无法运行”也不等于失败，但必须明确阻塞、影响和下一步。
DoD 表示分支交付物已经完整并可进入 Ready/merge；WORK 可在最终 PR 提交中归档。随后
Ready、审批、auto-merge 和实际 merge 的真源是 PR/托管平台，不再用第二个关闭提交回写。

### 放弃终态

`abandoned` 是与 DoD 分离的终态：必须记录放弃原因、已保留结果、未满足验收、残余风险和
后续归属，移入 archive 后再次运行 Harness。它不得被描述为验收通过，不得把 PR 转为
Ready，也不得 merge；如需保留远端证据，只能维持/关闭 Draft 交接。

## 3. Git 自动化闸门

自动 Git 动作不是单纯的“命令成功”，必须满足对应闸门：

| 阶段 | 必须满足 |
| --- | --- |
| commit | 实施已授权；exact base SHA/ancestry 已验证；聚焦工作分支；只含 clean/absent 起始且归属明确的任务路径或纯 Agent patch；单一意图；WORK/REQ 已同步；差异、秘密、异常文件和风险相称检查通过 |
| push | commit 闸门有效；分支点 base、当前 protected tip 与候选策略取严格交集；canonical fetch/push URL/refspec 匹配；当前任务分支；未评审分支 CI 无生产秘密/高权限；没有未经独立批准的治理/远端执行路径或新增敏感内容 |
| Draft PR / Ready | PR 唯一且正文证据同步；Ready 还要求 `done` 的 DoD 对 exact head 成立；`abandoned` 永不 Ready；merge 尚未发生不阻断 Ready |
| 自动 merge | 三方策略交集仍允许；仅轻微/标准；changed-files、CI、非作者批准、风险证据均绑定 exact head；新 push 撤销旧批准；`main` 保护启用；平台支持 expected-head 原子 merge；PR 可安全合并 |

闸门失败时保留真实状态，不通过 force、reset、rebase、隐藏文件或虚构证据推进下一阶段。
只有失败条件阻塞当前目标且需要用户决定时才询问；可由环境确认的事实自行检查。

## 4. 风险与验证矩阵

| 变化类型 | 最低验证 |
| --- | --- |
| 仅文档/Harness | Harness 检查、链接检查、内容自审 |
| React/TypeScript 纯逻辑 | 格式/静态检查、相关单元测试 |
| UI 交互 | 上述检查、组件测试、键盘/可访问性检查 |
| Rust 纯逻辑 | `fmt`、`clippy`、相关单元测试 |
| 文件/路径/监听 | Rust 集成测试；临时目录；越界、外部变化、失败恢复 |
| Git 适配 | 临时 Git 仓库集成测试；空仓库、脏状态、冲突、凭据/超时 |
| Markdown/本地资源 | 恶意 Markdown、协议、CSP、路径与隐私回归 |
| IPC/跨层契约 | 两端类型/序列化测试、错误码、取消与 E2E |
| 依赖/架构/数据格式 | REQ + ADR、替代方案、许可证/安全、迁移与回退验证 |
| 发布/安装 | 干净 Windows 测试机安装、升级/卸载、核心 E2E |

代码工程尚未初始化时，不预设具体 package scripts。初始化后应把真实命令写入 manifest，
并更新本表；精确命令只维护在 manifest 和 CI，避免本文漂移。

## 5. 安全阻断项

出现以下任一项不得宣称完成：

- 可以通过路径、符号链接或大小写差异越过授权工作区。
- WebView 可以执行任意命令、远程脚本或未经允许的原始 HTML。
- 日志、错误、快照或测试夹具泄露正文、凭据或个人信息。
- 文件冲突会静默覆盖任一方。
- Git 操作可能强制推送、重写共享历史或隐藏部分失败。
- 数据迁移没有来源副本、失败报告或恢复路径。

## 6. 证据格式

在 WORK 的验证表中记录：

| 字段 | 要求 |
| --- | --- |
| 检查/命令 | 可重复的准确命令或人工步骤 |
| 结果 | `passed`、`failed`、`not-run`，不能使用含糊措辞 |
| 证据 | 关键计数、测试名、报告路径或观察结果；不粘贴秘密/大量日志 |
| 说明 | 失败原因、未运行原因、环境限制与残余风险 |

只引用终端曾经成功的记忆不够；下一位成员必须能从 WORK 看出何时、如何、对什么版本
做过验证。

## 7. 评审深度

- 轻微变更：本地完成可由作者自审，除非涉及规范措辞；远端自动 merge 仍需要当前 HEAD 的
  非作者批准。
- 标准变更：至少一位非作者评审需求符合性和实现/测试。
- 重大变更：产品/技术责任人分别评审范围与决策；安全边界变化需要安全视角；重大变更
  永不自动 merge。
- 紧急变更：止损后补非作者复核和回归证据，不能长期保留临时绕过。
