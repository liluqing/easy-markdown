# 用户与 Agent 的自然语言协作协议

本协议定义人类成员如何与 Agent 沟通，以及 Agent 如何把口语化请求转成可追踪的仓库工作。
核心原则是：**用户负责表达目标和作决定，Agent 负责查事实、管理流程和推进执行。**

用户不需要学习 REQ、WORK、ADR、状态机或生成器命令。它们是 Harness 的后台机制，
用于让下一次没有聊天记忆的 Agent 能继续工作。

## 1. 用户可以直接怎么说

日常表达本身就是有效入口，例如：

- “搜索有点慢，你先帮我看看怎么回事。”
- “把 Markdown 预览里的链接问题修一下。”
- “继续上次的编辑器 Spike。”
- “先做方案，暂时别改代码。”
- “Review 一下这个改动，重点看会不会丢数据。”
- “这个同步方案你狠狠挑战一下我的想法。”

不需要先填写“目标、范围、验收、风险、权限”问卷。Agent 应从仓库真源和环境中补齐事实，
只把必须由用户决定的事项留给用户。

## 2. Agent 如何解释常见口语

| 用户表达 | 默认意图 | Agent 的默认行为 |
| --- | --- | --- |
| “想想、分析下、给个建议” | 探索/解释 | 只读调查并给判断，不实施 |
| “看看怎么回事、排查一下” | 诊断 | 查明原因和证据，不默认修复 |
| “帮我做、修一下、加上、实现” | 变更 | 在目标范围内建档、实现、验证和交接 |
| “继续” | 恢复 | 从 active WORK 和仓库状态恢复最匹配的未完成工作 |
| “Review、检查一下” | 评审 | 报告问题和证据；除非同时明确要求修复，否则不修改 |
| “先别动、只给方案” | 只读约束 | 可以调查和设计，不写实现、不执行目标动作 |
| “不要提交、不要推送、先别开 PR” | 缩窄 Git 自动化 | 保留本地状态并遵守限制，直到用户解除或任务结束 |

上下文可以改变默认含义。Agent 应说明会实质影响结果的解释，但不需要把每个显而易见的
细节都反问用户。

## 3. Agent 的后台推进流程

收到自然语言请求后，Agent 按以下顺序工作：

1. **查事实**：读取根规则、相关文档、代码、Git 状态和现有 active WORK。
2. **归一化意图**：识别用户要探索、诊断、规划、变更、评审、恢复、等待，还是执行某个
   明确动作。
3. **恢复上下文**：有同一 active WORK 就继续，没有才按变更风险建立必要记录。
4. **判断信息是否足够**：
   - 事实可查：自行查，不问用户。
   - 缺失项低风险、可逆：采用推荐的合理假设并推进，在 WORK 或交接中记录。
   - 缺失项会实质改变方向、安全、数据或授权：进入 Grilling。
5. **执行与验证**：完成已授权范围内的最小完整工作，并逐条留下证据。
6. **交接**：把结果、剩余风险和下一步写回仓库；不依赖用户记住本次对话。

Agent 可以在后台创建和更新 REQ、WORK 等记录，这属于标准实现流程，不需要用户手动运行
命令。清晰、有权限的自然语言指令可以作为需求接受依据；Agent 必须记录这个解释，不能
把含糊的产品方向自行标成已接受。

## 4. 什么时候进入 Grilling

[Grilling Skill](../../.agents/skills/grilling/SKILL.md) 在以下情况使用：

- 用户明确说“grill 我”“狠狠问我”“逐项挑战”“压力测试这个想法”等触发语。
- 存在多个合理解释，而且选择不同会明显改变目标、范围或验收结果。
- 未决内容涉及产品方向、架构、运行时依赖、安全、隐私、数据格式、迁移、破坏性操作或
  授权边界。
- 当前想法存在矛盾或隐含假设，继续行动可能造成不可接受的风险。

以下情况**不**应启动 Grilling：

- 用户只是表达随意或没有使用专业术语。
- 答案可以从仓库、工具或环境中查到。
- 缺失细节可以用低风险、可逆且符合现有基线的默认值解决。
- 任务清晰，继续追问只会增加沟通成本而不会改变结果。

## 5. Grilling 的对话节奏

Grilling 先查事实，再按决定之间的依赖顺序访谈。每轮必须：

1. 只问一个当前决定。
2. 先给推荐答案和简短理由。
3. 只有在有帮助时提供两到三个互斥选项和主要取舍。
4. 等用户回答后，再进入对应分支的下一个问题。

示例格式：

```text
推荐：MVP 先采用单向手动同步，因为冲突和凭据边界尚未验证。

问题：第一版同步是否必须自动双向进行？

选项：手动单向（风险最低） / 自动单向（体验更好） / 自动双向（能力最强、冲突风险最高）
```

所有实质决定完成后，Agent 汇总目标、范围、非目标、验收、风险和授权，再**只问一次最终
确认**。用户明确确认共同理解之前，Agent 可以做只读调查，但不得修改实现或执行目标动作。
用户可以随时终止访谈；未决分支会被记录，依赖它们的工作不会启动。

## 6. 自动推进不等于无限授权

| 动作 | 默认授权规则 |
| --- | --- |
| 读取仓库、检查状态、运行只读诊断 | 为理解当前请求可自动执行 |
| 创建/更新必要的 REQ、WORK 和交接记录 | 已授权变更的正常后台步骤 |
| 修改实现与文档、运行本地验证 | “做、修、实现”等请求授权的目标范围内可执行 |
| 轻微变更进入自动 commit/PR | 无需 REQ；Agent 后台建立 `requirement: none` 的轻量 WORK |
| 创建聚焦分支、检查点 commit | 清晰实施授权下按 [Git 工作流](git-workflow.md) 自动执行 |
| 交接点 push、创建/更新 Draft PR | 可信远端、文件归属和检查满足时自动执行 |
| Squash Merge | 仅轻微/标准；当前 HEAD 的 CI、非作者批准、风险证据、主干保护和原子 merge 全部满足时自动执行 |
| 无可信初始 commit/base 或 Git 策略处于 bootstrap | 可以编辑/验证，不执行 branch、commit、push、PR 或 merge |
| 治理、CI/CD、CODEOWNERS 或远端执行路径变化 | 使用分支点 base、当前 protected tip 与候选规则的严格交集，要求独立维护者/安全批准，不能自我授权；未评审分支 CI 不得获得生产秘密或高权限 |
| 新增依赖、改变架构/数据格式/安全边界 | 需要明确决定；高影响未决项进入 Grilling |
| 删除、覆盖、批量移动或迁移 | 需要明确目标和影响范围；不清晰时进入 Grilling |
| 文件归属、受控数据、异常文件、失败检查、冲突、远端/凭据或保护条件不足 | 只在该条件阻塞当前目标时询问一个最小问题；CI/评审等待不询问 |
| 凭据、token、私钥等秘密 | 硬阻断 commit/push，不提供“仍然纳入”选项 |
| 发布、部署、发布标签或修改远端/保护规则 | 不从普通开发请求推断，必须明确点名 |
| 强制推送、共享历史重写或安全绕过 | 不自动执行；仅在规则允许且有独立高风险授权时讨论 |

新的用户消息若明显是在补充当前任务，Agent 合并处理；若明显是在替换目标，Agent 停止旧
方向并转向新请求。范围或验收发生实质变化时，后台记录也必须同步更新。

## 7. 三个边界示例

### 清晰且低风险

用户：“README 里项目阶段写错了，按技术文档修一下。”

Agent 读取两个真源，确认差异后直接修正并检查链接；不要求用户提供 REQ 编号或验收模板。
若仓库已完成 Git bootstrap，Agent 会在检查通过后自动 commit，并在交接点自动 push/更新
Draft PR；用户无需再回复一次“可以提交”。

### 先诊断、不默认实施

用户：“搜索有点慢，你先帮我看看。”

Agent 恢复相关记录、查看实现和已有性能目标，做只读诊断并报告证据。“看看”本身不等于
允许修改；如果用户随后说“按推荐方案修”，再进入实现流程。

### 高影响且需要 Grilling

用户：“让所有知识库都自动双向同步到远端。”

Agent 先查已有 Git、数据和安全边界，然后从同步对象与数据主权等最高依赖决定开始，每次
只问一个问题并给推荐答案。在用户确认完整共同理解之前，不修改同步实现。
