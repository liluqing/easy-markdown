# Agent 跨会话恢复与交接协议

Agent 的会话记忆不可靠，仓库文件才是持久记忆。任何需要跨会话或多步骤完成的工作，都
必须使用 active WORK 保存可恢复状态。

## 1. 新会话恢复

每次进入仓库：

1. 阅读根 `AGENTS.md` 和 `README.md`。
2. 检查 Git 状态；把已有修改、暂存和未跟踪文件列为受保护上下文。
3. 搜索 `docs/work/active/`：
   - 有匹配 WORK：阅读完整内容并从“下一具体动作”恢复。
   - 有多个疑似匹配项：不要猜，记录重复并请负责人选择。
   - 无匹配项：按变更等级决定是否创建。
4. 阅读 WORK 链接的 REQ、产品/技术文档和 ADR。
5. 对照当前文件确认 WORK 是否陈旧；若不一致，先更新上下文快照。
6. 在实施前复述目标、范围、风险和计划，确保不是沿用过时聊天指令。

## 2. 工作中的持久检查点

出现以下事件后立即更新 WORK，不等到会话结束：

- 完成一个可验证步骤。
- 验收标准、范围或非目标改变。
- 选择或否决一项重要方案。
- 发现用户已有改动、兼容问题、安全风险或隐藏依赖。
- 测试失败、环境不可用或需要外部决定。
- 下一步不再是原计划中的动作。

更新应写事实和证据，不写“处理了一些问题”“差不多完成”等无法恢复的描述。

## 3. 阻塞协议

阻塞时：

1. 将 WORK 状态改为 `blocked`。
2. 记录已经确认的事实、已排除原因和复现方式。
3. 写明阻塞条件由谁/什么解除。
4. 提出一个最小、明确的待决问题。
5. 写下阻塞解除后的第一条命令或编辑动作。

不要因为“最好再确认一下”就停止可安全推进的只读分析；也不要在需要产品授权、安全许可
或破坏性操作批准时自行假设。

## 4. 标准交接内容

每个 WORK 的交接段必须包含：

- **当前状态**：planned / in-progress / blocked / review / done / abandoned。
- **目标与范围**：一两句话，链接 REQ。
- **已完成**：可验证结果，不只列活动。
- **未完成**：按优先顺序列出。
- **下一具体动作**：下一位成员无需重新调查即可执行的一步。
- **修改路径**：已改动或新增的文件。
- **验证证据**：命令、结果、未运行项。
- **决定与假设**：已确认、临时假设和仍待批准项分开。
- **风险与阻塞**：影响、所有者和解除条件。
- **工作区保护**：不属于本 WORK、不得覆盖的用户改动。
- **Git 状态**：当前/上游分支、HEAD、base ref/SHA、owned paths/初始状态、未提交/未跟踪
  状态、最后成功 commit 与 push。
- **PR 状态**：链接、Draft/Ready、exact head、changed-files、检查、当前 HEAD 的评审、风险
  等级、自动 merge 条件及下一安全动作；`abandoned` 必须标记为永不 Ready/merge；无远端
  时明确写 `not-run`，不虚构链接。

聊天中的总结可以帮助阅读，但不能替代上述仓库记录。

## 5. 完成交接

即使任务已经完成，也要保留交接：

1. 确认产品/技术真源已经更新，不能让 archive WORK 成为唯一的新事实。
2. 记录验收标准与证据映射。
3. 把未完成的后续事项建成新 REQ/WORK 或明确列为残余风险。
4. 选择一个终态：完成交付设为 `done`；停止交付则记录原因、未满足验收、残余风险和后续
   负责人后设为 `abandoned`。
5. 归档 WORK，再对归档后的最终状态运行 Harness 检查。

只有 `done` 可以继续到 PR Ready/merge。`abandoned` 不满足 DoD；远端只能保留/关闭 Draft
交接证据，不得转为 Ready 或 merge。

会话暂停、跨人交接或 PR-ready 是 [Git 工作流](git-workflow.md) 的自动 push 点。若当前
检查点满足提交/推送闸门，Agent 自动 commit、push 并更新 Draft PR，不询问用户；若文件
归属、检查、远端、冲突或保护条件阻止自动化，则保留状态、记录证据，并只在它阻塞当前
目标时提出一个最小问题。

归档不是删除。它保留本次执行的证据，但后续成员应优先阅读当前基线与新的 active WORK。
